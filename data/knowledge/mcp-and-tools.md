# MCP 与工具协议

## MCP 是什么

MCP 全称 Model Context Protocol，是 Anthropic 提出的开放协议，用来标准化"模型如何访问外部数据和工具"。它解决的问题是：以前每接一个工具就要写一套适配代码，工具一多就变成 N 乘 M 的胶水层；有了统一协议，工具方按协议实现一个 server，模型侧就有统一的 client 去连。

MCP 里有三个角色：client（模型这一侧的应用）、server（提供能力的一方）、host（承载 client 的宿主程序）。server 暴露三类能力：tools（可执行的函数）、resources（可读取的数据）、prompts（预置的提示词模板）。

## MCP 和 Function Calling 的区别

Function Calling 是模型层面的能力：模型输出"我要调什么函数、传什么参数"。MCP 是工程层面的协议：规定这些工具从哪来、怎么被发现、怎么被调用。

可以这样理解：Function Calling 解决"模型会不会调"，MCP 解决"工具从哪来、怎么接"。两者不冲突，MCP server 里的 tools 最终还是要转成 Function Calling 的 schema 交给模型。

## 工具权限与沙箱

工具一旦能执行代码或读文件，风险就从"答错"升级成"造成破坏"。所以工程上必须做三件事：第一，白名单，只允许调用注册过的工具；第二，参数校验，类型、范围、枚举都要在 schema 里写死，服务端再校验一次；第三，超时与资源限制，单个工具执行不能无限跑，也不能无限占用内存。

涉及文件、数据库、支付这类高权限操作，一定要加人工确认环节，不能让模型直接执行。

## 并行工具调用

当模型一次返回多个 tool_calls，且这些工具之间没有依赖，可以并发执行，执行完一起回填。这样能把多工具场景的延迟从"串行求和"降到"取最大值"。

但要注意：如果工具之间有依赖（比如先查用户 id 再查订单），就必须串行，让模型分两步调用。判断标准写在工具描述里，让模型自己知道先后关系。

## 工具返回的格式

工具结果会被拼进上下文喂给模型，所以格式直接影响理解成本。三个建议：一是结构化，用 JSON 而不是自然语言长文；二是裁剪，只返回需要的字段，不要把整个数据库行丢进去；三是标注单位，金额写清楚是分还是元，时间写清楚时区和格式。
