# LLM 应用的工程化

## 调用层要处理哪几类错误

调用大模型接口会遇到四类问题：网络超时、限流 429、服务端 5xx、参数或鉴权错误。

前三类是可恢复的，应该重试，等待时间指数递增，比如 2 秒、4 秒、8 秒，最多重试三次。第四类不可恢复，重试一万次也一样，应该直接抛出，让工程师去改。

一个常见的错误做法是无差别重试所有异常，结果鉴权失败了还在疯狂重试，既浪费时间又可能把账号打到风控。

## 流式输出怎么实现

流式输出用 SSE（Server-Sent Events）：服务端保持一个长连接，按 `data: {...}\n\n` 的格式不断推 token，前端收到就渲染。相比一次性返回，用户感知的首字延迟从"整段生成完"降到"第一个字生成完"。

实现要点：一是要处理结束标记（`data: [DONE]`），二是要处理中途异常，三是前端要能做增量渲染而不是每次重绘整段。

## 成本怎么控

大模型的成本由输入 token 和输出 token 共同决定，其中输入往往是大头，因为每次请求都要带上历史对话和检索到的资料。

三个抓手：第一，压缩上下文，只带相关的历史，检索结果限制条数和长度；第二，缓存，相同问题直接返回缓存结果，语义相近的用向量缓存；第三，选模型，简单任务用小模型，复杂任务才用大模型，按难度路由。

按量计费的项目一定要做 token 统计和日志，否则月底账单会莫名其妙。

## 并发与限流

线上服务要防两类问题：一是自己把上游打爆（超过对方的 QPS 限制），二是被用户打爆（突发流量）。

前者用客户端限流，比如令牌桶，把请求速率控制在配额以内；后者用服务端限流，按用户或 IP 限制频率，超了返回 429 并提示稍后再试。

还要注意重试风暴：一个请求失败触发了三次重试，流量瞬间放大三倍。解法是重试加随机抖动，并且限制同时重试的数量。

## 日志与可观测

一个可用的 LLM 应用至少记录四样东西：请求 id、完整 prompt、模型返回、耗时与 token 数。

出问题时这四样能还原现场：是检索没召回，还是召回了但模型没用好，还是模型返回格式不对。没有日志的 LLM 应用，调起来全靠猜。

## 上线前要做的检查

第一，准备一个评估集，至少二十条，覆盖主要场景和边界情况；第二，做回归测试，每次改 prompt 或换模型都跑一遍，确保不比上一版差；第三，准备降级方案，模型接口挂掉时要有兜底话术，而不是直接报错给用户；第四，做灰度，先放 10% 流量观察。
