# AI Agent 开发笔记

## 一、Function Calling 是什么

Function Calling 是让大模型在对话中主动调用外部函数的能力。流程分四步：第一步，开发者用 JSON Schema 描述每个工具的名字、用途和参数；第二步，把这些 schema 随对话一起发给模型；第三步，模型判断需要调工具时，不直接回答，而是返回一个 tool_calls 结构，里面写清楚调哪个函数、传什么参数；第四步，开发者在本地执行这个函数，把结果以 role=tool 的消息回填给模型，模型再基于结果生成最终回答。

关键点是：模型不执行任何代码，它只输出"要调什么"。真正的执行永远在开发者这一侧。所以工具的安全性由开发者负责，模型只负责决策。

多轮工具调用是指模型在一次回答里返回多个 tool_calls，或者拿到结果后继续调下一个工具。实现上通常用一个 while 循环：只要返回里有 tool_calls 就继续执行并回填，直到模型给出纯文本回答。循环必须设最大轮次，否则模型反复调同一个工具会死循环。

## 二、工具设计的三条原则

第一，工具描述要写清楚"什么时候用"，不只是"能做什么"。模型是看着描述做选择的，描述里写"当用户询问实时天气、需要按城市查询时使用"，比写"查询天气"命中率高很多。

第二，工具失败时返回错误文本，不要抛异常。把"城市未找到"作为结果回填给模型，模型往往能自己换个城市重试或者向用户说明原因；一旦抛异常打断链路，整个对话就断了。

第三，工具要有明确的输入约束。用 schema 限定类型和枚举值，比让模型自由发挥稳得多。计算类工具尤其要注意，不要用 eval 执行模型给的字符串，用 AST 白名单只放行四则运算和常量。

## 三、RAG 的切块策略

切块是 RAG 效果的第一决定因素。最稳的做法是分层切：先按文档结构切，比如 Markdown 的标题、PDF 的章节、HTML 的小节；一节还是太长，再按句子切。

块大小一般取 300 到 800 字。太小会丢上下文，语义不完整；太大召回精度下降，一条无关内容会稀释整块的相关性。中文一句话大约 20 到 40 字，500 字大约是十几句话，正好覆盖一个完整话题。

块之间要留重叠，通常是块大小的 10% 到 20%。重叠的作用是防止答案刚好被切在边界上，一半在前块一半在后块。500 字块配 80 字重叠是比较常用的配置。

每个块要带元数据：来源文件、章节标题、块序号。检索时把标题一起拼进去，命中率会明显提升，因为标题本身就是概括。

## 四、向量检索与关键词检索

向量检索把文本编码成稠密向量，用余弦相似度找最近邻。优点是能处理同义表达，"怎么退款"和"退货流程"在向量空间里距离很近。缺点是需要 embedding 模型，有计算成本和内存开销，而且对专有名词、编号、代码符号不敏感。

关键词检索（BM25、TF-IDF）靠词频匹配，优点是零成本、可解释、对专有名词很准。缺点是完全不懂同义词，用户换个说法就召不回来。

所以生产系统通常做混合检索：两路各取 Top-N，再用 RRF（Reciprocal Rank Fusion）融合。RRF 的公式是每个文档的得分等于 Σ 1/(k + rank)，k 一般取 60。这样做的原因是两路的分数尺度不可比，直接加权相加没有意义，而按排名融合不需要归一化。

检索完之后还可以加重排（rerank），用交叉编码器对 Top-20 重新打分，把最相关的几条顶上来。代价是延迟增加。

## 五、上下文管理与记忆

大模型的上下文窗口有限，长对话必然要裁。最粗暴的做法是按条数截断，保留最近 N 条，简单但会浪费——一条长回答可能顶十条短消息。

更合理的做法是按 token 预算裁剪：先用 tiktoken 之类的工具算出每条消息的 token 数，从最新往前累加，超过预算就停。系统提示词必须始终保留，它是人设和规则，丢了整个行为就变了。

裁剪掉的历史不要直接扔。可以把更早的对话压成一段摘要，放在系统提示词后面，这样既省 token 又保留了关键信息。

长期记忆是另一层：把用户明确说过的事实（称呼、偏好、项目背景）抽出来落盘，下次会话读回。注意写入要有门槛，闲聊不要写，否则记忆会被噪声污染，越用越乱。

## 六、怎么评估 RAG

最基础的指标是 Hit@K：对每个问题，看正确答案所在的那个块有没有出现在召回的前 K 条里。K 一般取 3 或 5。Hit@3 等于命中的问题数除以总问题数。

比 Hit@K 更细的是 MRR（Mean Reciprocal Rank）：命中排第 1 得 1 分，排第 2 得 0.5 分，排第 3 得 0.33 分，没命中得 0 分，最后取平均。它同时衡量"召没召回来"和"排得靠不靠前"。

评估集要自己写，一般 20 到 50 条起步，每条包含问题和它应该命中的文档块。没有评估集的时候，调参全靠感觉，改一个参数不知道是变好还是变坏。

端到端还要看生成质量：答案有没有引用来源、有没有编造、拒答是否合理。这些只能人工抽检，或者用大模型当裁判打分。

## 七、常见失败模式

第一类是召回失败：知识库里明明有答案，但检索没找到。原因通常是切块不合理，或者用户问法和文档措辞差太远。解法是混合检索加 query 改写。

第二类是幻觉：检索为空或者召回的是无关内容，模型仍然硬答。解法是强制要求"只依据给定资料回答，资料里没有就说没有"，并且在检索分数低于阈值时直接拒答。

第三类是引用错位：答案引用了编号，但编号对应的内容和结论对不上。解法是生成后做一次校验，检查每个引用编号指向的块是否真的包含关键词。

第四类是上下文溢出：长文档塞进 prompt 直接把窗口撑爆。解法是控制召回条数和单块长度，必要时对召回内容再做一次压缩。

## 八、设计一个客服 Agent 的拆解思路

先拆角色：用户、客服 Agent、知识库、工单系统、人工坐席。Agent 负责理解问题、查知识库、判断能不能自助解决。

再拆流程：收到问题先做意图分类（咨询、售后、投诉、闲聊），咨询类走 RAG 检索知识库，售后类调订单查询工具，投诉类直接转人工并生成工单摘要。

然后定边界：哪些必须转人工（涉及退款金额、法律纠纷、情绪激烈），这些要写成硬规则，不能交给模型自由判断。

最后定评估：自助解决率、平均轮次、转人工率、用户满意度。上线前用历史工单做回归测试，确保新版本不比旧版本差。
